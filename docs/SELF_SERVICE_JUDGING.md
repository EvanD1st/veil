## What is implemented

### Judge access and auction modes

Follow-up: [seller enrollment](SELLER_SETUP.md) adds address-only requests, pending/ready UI, private operator queue and migration 0009. Approval still requires private viewing-key import, rescan and matching website/scanner configuration; requesting setup alone cannot enable paid listings.

Any authenticated account can act as the seller; no judge/admin role is needed. A judge with an approved, scanner-covered receiver can choose **Digital download · verified checkout**, upload their own preview and protected original, and publish a paid artwork auction. Other judge accounts can place sealed bids. After the seller publishes the verified winner, only that winner receives the exact testnet invoice. They pay the seller directly from a compatible external Zcash testnet wallet; the independent scanner must confirm the exact incoming Sapling address, amount, memo and output with active-chain confirmations before the protected download unlocks. This is not escrow, and the managed VEIL wallet's outgoing Pay path remains disabled.

A judge whose own receiver is not covered can still create a **practice auction** to test sealed bidding, seller reveal, and result verification. Practice auctions never accept a payment address or protected file and do not represent a completed sale. Coverage is currently an operator-approved list for receivers the scanner can observe; it is not self-service. Do not bypass that boundary by accepting an arbitrary address or redirecting proceeds to an operator wallet.

The ten Genesis collection auctions are opened only by the explicitly named owner account in the private operator config (`ownerUsername` must equal the login `username`). Each opens with a **0.01 ZEC testnet starting bid** (1,000,000 zatoshis) and a fixed **35-day** window. The public artwork previews alone are not seeded auctions; run the operator's `seed-all` only after the original-file manifest, owner identity, receiver coverage and release have been verified. The seeder is idempotent and does not replace completed/verified editions.

* Ten selected artwork families, featured first three and the ordered full gallery. Complete contained compositions, actual download dimensions/bytes, AI disclosure, license, edition and real persisted status. Existing hero/login animation, My bids, My purchases, native authentication, proof context/assets and scanner validation remain. Empty categories are not populated with invented Digital Items.
* A bounded ZIP importer verifies paths, types, duplicate/encrypted/link entries and decompression limits before reading the exact ten selected entries. Local inspection found 83 files: 70 variants and 13 sheets. Exact selected originals total **2,738,132 bytes**; metadata-free non-upscaled WebP previews total **220,124 bytes**. Originals and their integrity manifest are outside Git/public assets. Preview dimensions never imply increased source detail. The original First Seal is 640×645; the other actual sizes are in judging/collection.json. No NFT, scarcity, authorship verification, copyright transfer or Zcash endorsement is claimed.
* Private import verifies each original against a root-reviewed private manifest, and uses existing authenticated upload/draft/create endpoints. A specifically configured platform seller must already have its **own** scanner-observed receiver. No account is implicitly privileged. One current edition per family, five total per family, maximum 50 stored editions, normal eight-bid capacity. A normal real artwork auction defaults to 35 days (60 seconds–35 days configurable); its deadline is reserved once, never extended. Keys are durably backed up before opening bidding. Completed records and obligations are never overwritten.
* The operator initially seeds chosen families explicitly. Later editions require bounded authenticated judge demand (200 outstanding requests maximum), serviced at most once per minute; the worker does not generate an endless sequence of empty lots. An occupied/full/failed current edition is retained. A full edition still closes at its original deadline. Judges can queue a distinct successor; the worker opens it only after actual verified completion, never by dropping accepted bids or creating overlapping open editions.
* A separate supervised demo-seller worker uses real native cookie sessions and the existing browser encryption/drand/full-log prover/publication/verifier. One global durable lease and a kernel flock serialize proof/seed jobs. Private JWKs/journals are mode 0600 in a mode-0700 directory, never a web database or static route. A failed/malformed accepted bid blocks the whole tally. Publication intent is durably marked before clicking the existing single-write publication flow. On restart, stored verified results are reconciled before another job; an uncertain absent result is retained for operator review, never blindly republished. Ordinary sellers keep their own browser keys/reveal behavior.
* Private activation requests persist once per account (200 request cap), retain an honest blocked state and **null unavailable balance**, and confer no grant. Backup handling enforces session, exact Origin, password reauthentication and no-store, but refuses export until a safe individual recovery adapter exists. It never exports a master mnemonic. The native scanner bearer routes remain independent.
* The managed treasury now has a pinned Zingolib adapter path, but remains **closed for live spending** until its private validation evidence is produced. Synthetic tests cover grant limits, explicit invoice review/Pay authorization, source locks, prepared bytes/txid, a single-broadcast guard, uncertain outcomes and read-only recovery. These tests are not live payment evidence. No database credits are presented as balances. A sent state never creates an entitlement; only existing trusted scanner acceptance can do that.

## Exact installed-wallet gate

Read-only inspection on 26 October returned the approved experimental backend SHA-256 **27062b951bf0826c7067c57eebcdaab5509bc44dda39ed236d0c12e6408c35ab**, advertised account/import/PCZT methods, and strict synchronized readiness. The managed branch uses Zingolib's independent mnemonic-backed wallet path rather than Zallet's imported-key PCZT signing path. An actual funded-wallet restore was attempted in the bounded private service and failed before any signing or broadcast; its 11-byte encrypted diagnostic could not be classified. The source sender database remained unchanged, managed service remains disabled and no funds moved. This is the current live blocker, not evidence of a passing signing test. The installed base is 0d433b322408c30ee48765a98a81af9001108e7d plus the approved minimum-pool patch; failed cargo-vet evidence remains explicit in scanner/testnet/versions.json.

Source-derived compatibility findings:

1. [z_getnewaccount](https://github.com/zcash/zallet/blob/0d433b322408c30ee48765a98a81af9001108e7d/zallet-core/src/components/json_rpc/methods/get_new_account.rs) selects an existing backed-up seed. Exporting that shared master as a judge's individual backup would expose other accounts, and is prohibited here.
2. [z_importkey](https://github.com/zcash/zallet/blob/0d433b322408c30ee48765a98a81af9001108e7d/zallet-core/src/components/json_rpc/methods/import_key.rs) does support separately controlled Sapling spending keys and hot key reload. It is **not** accurate to say independent keys cannot be imported. However, such accounts lack seed derivation metadata; reimporting an already known key does not implement a general rewind of just that account.
3. [pczt_create](https://github.com/zcash/zallet/blob/0d433b322408c30ee48765a98a81af9001108e7d/zallet-core/src/components/json_rpc/methods/pczt_create.rs) records seed/account signing hints only when derivation metadata exists. [pczt_sign](https://github.com/zcash/zallet/blob/0d433b322408c30ee48765a98a81af9001108e7d/zallet-core/src/components/json_rpc/methods/pczt_sign.rs) derives its spending key from those hints. It does not select the separately encrypted imported key as a fallback. Thus the proposed independently restorable standalone-key path lacks the required durable PCZT signing flow in this exact build. No source patch or cryptographic workaround is installed.
4. Seed generation/import and [confirm-backup](https://github.com/zcash/zallet/blob/0d433b322408c30ee48765a98a81af9001108e7d/zallet-core/src/commands/confirm_backup.rs) use a CLI datadir lock and terminal workflow. An online independent-seed provisioning/backup service has not been reviewed or tested. Automated shared-master quiz answers, unconfirmed new mnemonics and stopping the receiving wallet per signup are not substitutes.
5. The direct async-send route does not supply the required durable pre-broadcast bytes/idempotency and caller fee cap. Existing escrow PCZT code additionally requires one exact deposit/no change; it cannot be relabelled as a multi-note user wallet. Managed-user selection/change/fee checks, individual restore, prepared-transaction recovery and an actual outgoing purchase remain unvalidated.

The code now contains an isolated Zingolib implementation for encrypted individual recovery, funded-wallet restoration, proposal signing and exact transaction inspection. It still needs a successful funded restore, a privately reviewed prepared transaction and a separately approved one-time testnet broadcast, then automatic scanner delivery and restart/reconciliation evidence. The live broadcast has not been approved by this feature request. Existing incoming-payment success and the sender's read-only balance observation do not satisfy this gate. Until those checks and a separate bounded funding-policy decision pass, **public starter grants and managed Pay remain disabled**, irrespective of environment flags. External-wallet invoice review remains available to actual winners.

The proposed separate unprivileged worker template allows one job, MemoryHigh 1,200 MiB, MemoryMax 1,536 MiB, swap max 128 MiB, CPU 50% of one core and 160 tasks. It refuses admission below 3 GiB MemAvailable and closes its own browser if availability drops below 1 GiB; it never restarts/kills a wallet/node. Kernel flock releases after crash/reboot. Exact CI process-tree peak measurements must be recorded before an isolated host trial; the whole browser-test peak is a conservative observation, not a sustained wallet-host approval. The template is **not installed/enabled** by this branch. No extra paid resources are requested.
