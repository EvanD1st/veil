## Runtime isolation and recovery

`/opt/veil-testnet` holds immutable application/tools and installed release binaries. `/var/lib/veil-build` contains disposable source/build material and preserved audit/resource evidence. `/var/lib/veil-testnet` contains the new state, separate receiver/sender directories, private signing key, service token, outbox and health records. The builder cannot read the runtime account's private directory. Co-located Zebra/Zallet/scanner services use one trusted dedicated runtime identity so private rotating RPC cookies and compatible state are accessible without publishing RPC or weakening file permissions.

The existing config generator creates explicit testnet-only settings, loopback node/wallet RPC and indexer ports, cookie authentication, `require_backup=true` and distinct wallet directories. `service.env` uses systemd syntax and contains paths; secret token bytes stay in a private file. It deliberately omits `VEIL_SCANNER_RECEIVER` until actual derivation from a backed-up wallet. New signer/service-token material was generated privately on AWS; it has not been installed in website configuration.

Unit templates under `scanner/testnet/systemd` provide orderly SIGINT shutdown, bounded restarts/start limits, memory/CPU limits and boot dependencies. All five runtime/timer units passed the host's `systemd-analyze verify`. The node and health timer are enabled; wallet/scanner remain disabled pending required wallet backup and integration configuration. The optional sender should remain stopped when unnecessary on this 8 GiB host. Service logs use a separate journal namespace capped at 256 MiB and seven days. Health timers test current testnet tip, wallet synchronization and disk reserve; a listener alone is not readiness. External alerts need a reachable authorized notification channel; journal records alone are not proof of alert delivery.

Recovery keeps existing wallet identities, mnemonic backups, service token, scanner key, outbox and Zebra state. Restart only the affected supervised unit; inspect readiness and chain/wallet agreement before resuming scans. A lost signed-report acknowledgement is retried from the same private outbox bytes. An expired outbox entry is discarded, never given a new expiration timestamp. Server-side leases expire after ten minutes, allowing a worker crash to recover; a restarted worker rechecks the chain before producing fresh evidence. No recovery path sends another payment.

## Outbound verification protocol

Seller/winner users submit an exact transaction ID and Sapling output index to `POST /api/auctions/:id/payment/scan`. The existing payment-access function derives the canonical published invoice and enforces role privacy first. An invoice has one immutable queued selector; duplicate submissions are idempotent and do not reset backoff. Correcting a mistaken selector requires operator review. Creation is bounded to five jobs per requester per hour and 1,000 active jobs, with thirty-day monitoring lifetime.

The AWS worker makes outbound HTTPS requests to `POST /api/scanner/jobs`. It opens no HTTP listener. A random 32-byte bearer token is kept in an owner-only AWS file; only its SHA-256 verifier and the trusted Ed25519 public key belong in website configuration. This token grants only queue claim, signed delivery and unavailable-state reporting. It cannot act as a seller/winner or bypass report verification. Rotation removes the old token's queue access; rotating the public key invalidates old signatures on normal status revalidation.

Claims are atomic SQLite/D1 statements with a single global expiring lease. The worker validates the invoice, configured actual receiver and existing read-only scanner checks. It signs the unchanged version-1 report only after exact incoming Sapling address/amount/memo/output/network binding, active-chain inclusion, confirmations, synchronization and race checks. The durable outbox is committed before delivery. The website verifies the configured signature, invoice, selected output, freshness, monotonic observation time and global output-reuse boundary before storing a report. Duplicate delivery only acknowledges identical previously accepted bytes; it never extends freshness.

Scans refresh every minute after delivery. Failures use bounded exponential backoff (15 seconds to five minutes); outages produce no fresh signature. Existing confirmation expires within five minutes even if the worker or website cannot be reached. A queued job or service heartbeat never confirms payment. A fresh valid `not-confirmed` report revokes prior confirmation. Payment metadata remains seller/winner-only; neither application logs nor public documentation contain real invoice/report/transaction metadata.
