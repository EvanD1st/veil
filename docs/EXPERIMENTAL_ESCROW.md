# Experimental TESTNET operator-custodied escrow design

This design is recorded before implementation. Feature and executor default off. Direct auctions remain direct. No live transfer, synchronization change, wallet creation or deployment is authorized by implementation.

Custodian controls funds and can observe receiving-wallet payments. This is not trustless, audited, insured or mainnet-ready. Auction proofs establish a result, not delivery or quality. Normal settlement requires seller declaration plus explicit buyer release. Silence never authorizes spending. Disputes block normal settlement; a distinct settlement-operator allowlist may decide full release/refund with a reason, never partial settlement. Account-list administrator status confers no settlement power.

States are separate: funding (unverified/current/uncertain), fulfillment (awaiting/seller-declared), dispute (none/open/reviewed), settlement (none/requested/preparing/prepared/broadcast-unknown/submitted/confirmed/frozen). A durable ledger retains deposit identity after scanner expiry; expiry or revocation freezes use without erasing the obligation. A requested intent is cancellable by dispute; once an executor atomically commits preparation, dispute/cancellation requires operator reconciliation. Browser code cannot commit preparation.

All monetary values are integer zatoshis. One exact output can back one invoice globally through the existing unique payment_reports output key plus a permanent escrow ledger claim. No queued selector, stale report or heartbeat credits funds. Late exact deposits are held for review; split, excess, partial, duplicate and unmatched deposits are quarantined, not silently credited/refunded. The winning amount includes shipping or pickup; a capped network fee is deducted from that amount. Unspent remainder/change stays attributable to the order until explicitly reconciled; it is never another order's available balance.

Creation snapshots fulfillment terms, TESTNET deposit address, fee cap and seller payout destination. Order creation requires a published proof-verified winner. Buyer supplies a checksum-valid Sapling TESTNET refund destination before authorization. Destinations freeze at authorization; changes require cancelling an uncommitted intent and renewed party authorization/operator review. This version conservatively refuses changes after a settlement request. Private delivery information and tracking are participants-only; settlement operators gain order access only for an open dispute. Tracking is an unverified seller claim, never server-fetched. Retain private details for 30 days after settlement then an operator-reviewed purge; retain financial/audit records for reconciliation. Backups contain sensitive details and follow the same access restrictions.

## Wallet capability evidence (pinned source, not live spending evidence)

Base: 0d433b322408c30ee48765a98a81af9001108e7d plus the separately approved minimum-pool patch; failed cargo-vet evidence remains in scanner/testnet/versions.json. Source inspected from https://github.com/zcash/zallet/tree/0d433b322408c30ee48765a98a81af9001108e7d/zallet-core/src/components/json_rpc .

- get_address_for_account derives wallet receivers; no wallet is initialized by this feature. An operator-provisioned TESTNET deposit receiver is configured privately.
- z_sendmany returns an operation ID and computes fees internally; its fee argument must be null. The asynchronous operation queue is in memory. It supplies neither a documented client idempotency key nor a caller fee cap. Do not retry after timeout.
- z_sendfromaccount combines PCZT creation/signing/extraction and broadcast; it is not used here.
- PCZT create/prove/sign/inspect/combine/extract methods exist. Inspection exposes fee_zat; extraction returns raw transaction/txid and indicates whether it stored pending-spent notes. This is a potential recoverable staged path, not proof that this integration safely selects/reserves only the intended order's deposit.
- Blocker: no implemented and live-validated adapter yet proves exact deposit-to-selected-note mapping, account/change isolation, fully checked PCZT recipients/fees/inputs, persisted pre-broadcast transaction recovery, node broadcast/reconciliation and crash behavior. Therefore the shipped executor refuses all live execution and loads no spending credentials. Synthetic adapter tests do not remove this blocker.

## Migration / rollback / eventual trial

Apply additive migration 0005 only after a consistent SQLite backup and offline review. Keep all escrow tables, events, ledger rows and intents during code rollback. Never restore an older database over unsettled obligations. Disable creation first, stop settlement worker, export outstanding liabilities privately and reconcile every prepared/unknown transaction before any rollback. Old code must not run while it could present escrow auctions as direct payments; keep the escrow-aware reader or disable auction/payment access. No destructive down migration is supplied.

Trial gates: review draft PR/CI; separately approve offline migration/release; provision and back up isolated testnet custody wallet manually; independently verify source/RPC schemas and implement the currently disabled PCZT adapter; test one order at a time with capped funds and exact approved transfer; validate deposit/reorg/readiness, fees, input isolation, crash-before/after preparation, lost ACK, kill switch, payout/refund inclusion and restart recovery. No mainnet funds.

Recovery: stop new settlements with the kill switch; preserve DB/WAL, encrypted wallet backups, executor journals and prepared bytes before investigation. Reconcile liabilities by order and compare wallet funds plus pending transactions. Restore wallet/database/journals consistently, inspect unknown broadcasts by persisted txid, never issue a replacement send blindly. On key compromise stop all settlements and deposit creation, isolate secrets, reconcile outstanding claims, rotate keys under operator-approved custody recovery. No automatic refunds, release deadlines or resolution guarantees.
## Private server configuration

`VEIL_EXPERIMENTAL_TESTNET_ESCROW=1` permits new escrow auctions only with checksum-valid `VEIL_ESCROW_DEPOSIT_ADDRESS` configured. Neither setting is enabled by default. `VEIL_ESCROW_OPERATOR_IDS` is a separate, explicit account-ID allowlist for disputed orders; never copy the account-list admin allowlist implicitly. `VEIL_ESCROW_SETTLEMENTS_ENABLED` defaults off; setting it does NOT enable the hard-disabled live executor. Disabling new creation must not hide existing liabilities or participant order access.

The executor source is isolated under `escrow/` and is not imported by the website or scanner. Its only executable settlement implementation is named `SyntheticSettlementEngine`, requires an explicitly synthetic adapter and is for fixtures only. The live factory always refuses execution, irrespective of environment flags. No spending credentials are provisioned/read. `node escrow/reconcile.mjs ABSOLUTE_PRIVATE_DB` provides a read-only metadata/count/liability summary; it does not establish wallet spendability. No payout/refund is claimed implemented at the wallet boundary.

Unsupported deposit observations: the exact read-only scanner refuses wrong/mismatched outputs, so it cannot discover or refund arbitrary unmatched wallet receipts. Those remain uncredited custody funds. Record exception categories privately and reconcile wallet receipts manually under a future authorized trial. Accepted late exact deposits automatically enter the exception ledger and cannot authorize release. Duplicate delivery cannot add credit; additional outputs cannot replace a bound output. Partial/excess reports are rejected, not treated as an installment or surplus refund. Any manual repair must append a reviewed exception/audit entry, never edit a permanent claim.
